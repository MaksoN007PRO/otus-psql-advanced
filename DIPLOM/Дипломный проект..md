# 2. ТЕОРЕТИЧЕСКАЯ ЧАСТЬ

# 2.1 PostgreSQL High Availability

PostgreSQL поддерживает несколько механизмов отказоустойчивости:
- потоковую репликацию;
- передачу WAL-журналов;
- hot standby;
- синхронную и асинхронную репликацию.

Потоковая репликация позволяет репликам получать WAL-записи с основного сервера PostgreSQL.

Это обеспечивает:
- резервирование данных;
- уменьшение вероятности потери транзакций;
- быстрое восстановление после сбоя.
# 2.2 Kubernetes StatefulSet

Для приложений с сохранением состояния Kubernetes использует StatefulSet.

StatefulSet обеспечивает:
- постоянные сетевые имена;
- постоянное хранилище данных;
- предсказуемые имена pod;
- сохранение состояния приложения.

Для PostgreSQL StatefulSet особенно важен, поскольку:
- база данных хранит состояние;
- данные должны сохраняться после перезапуска pod;
- репликация требует стабильных сетевых имен.
# 2.3 RTO и RPO

# 2.3.1 RTO

Recovery Time Objective - максимально допустимое время восстановления сервиса после отказа.

Формально:

```
RTO = время восстановления write availability
```
# 2.3.2 RPO

Recovery Point Objective - максимально допустимый объем потери данных.

Формально:

```
RPO = объем потенциально потерянных транзакций
```

Минимальный RPO достигается за счет:
- потоковой репликации;
- минимальной задержки репликации;
- быстрой передачи WAL-записей.

# 5.3 Развертывание PostgreSQL primary

Для PostgreSQL использовался StatefulSet.

Файл:

```
manifests/primary/postgres-primary.yaml
```

Содержимое:

```
apiVersion: apps/v1
kind: StatefulSet

metadata:
  name: postgres-primary
  namespace: pg

spec:
  serviceName: postgres-primary

  replicas: 1

  selector:
    matchLabels:
      app: postgres-primary

  template:
    metadata:
      labels:
        app: postgres-primary

    spec:
      containers:
      - name: postgres

        image: postgres:16

        ports:
        - containerPort: 5432

        env:
        - name: POSTGRES_USER
          value: postgres

        - name: POSTGRES_PASSWORD
          value: postgres123

        - name: POSTGRES_DB
          value: app_db

        - name: PGDATA
          value: /var/lib/postgresql/data/pgdata

        volumeMounts:
        - name: postgres-data
          mountPath: /var/lib/postgresql/data

        args:
          - "-c"
          - "wal_level=replica"
          - "-c"
          - "max_wal_senders=10"
          - "-c"
          - "max_replication_slots=10"
          - "-c"
          - "hot_standby=on"

  volumeClaimTemplates:
  - metadata:
      name: postgres-data

    spec:
      accessModes:
        - ReadWriteOnce

      resources:
        requests:
          storage: 5Gi
```

Применение:

```
kubectl apply -f manifests\primary\postgres-primary.yaml
```

# 8.2 Создание pgbench workload

Файл:

```
manifests/load/pgbench.yaml
```

Содержимое:

```
apiVersion: batch/v1
kind: Job

metadata:
  name: pgbench
  namespace: load

spec:
  template:
    spec:
      restartPolicy: Never

      containers:
      - name: pgbench
        image: postgres:16
        
        env:
        - name: PGPASSWORD
          value: postgres123

        command:
          - bash
          - -c
          - |
            echo "Initializing pgbench..."
            pgbench \
              -h postgres-primary.pg.svc.cluster.local \
              -U postgres \
              -d app_db \
              -i \
              -s 50
            echo "Starting benchmark..."

            pgbench \
              -h postgres-primary.pg.svc.cluster.local \
              -U postgres \
              -d app_db \
              -c 20 \
              -j 4 \
              -T 600 \
              -P 5
```

```
kubectl drain docker-desktop --ignore-daemonsets
```

# 11.2 Полученные сообщения Kubernetes

Во время drain были получены сообщения:

```
cannot delete Pods that declare no controllercannot delete Pods with local storage
```

# 11.3 Выявленные ограничения

| Компонент           | Причина                  |
| ------------------- | ------------------------ |
| storage-provisioner | системный pod            |
| vpnkit-controller   | компонент Docker Desktop |
| Grafana             | local storage            |
| Pushgateway         | emptyDir storage         |

# 11.4 Анализ "node failure experiment"

Эксперимент показал:
- single-node Kubernetes имеет ограничения отказоустойчивости;
- local storage ограничивает перенос workload;
- Docker Desktop Kubernetes не подходит для полноценной production-среды.

При этом:
- PostgreSQL pods остались доступны;
- реплики продолжили работу;
- система мониторинга сохранила работоспособность.

# 11.5 Практический инженерный вывод

Для полноценной отказоустойчивости Kubernetes необходимы:
- multi-node cluster;
- distributed storage;
- автоматическое переключение реплик..
